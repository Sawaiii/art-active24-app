# Art-Active24 — мобильное приложение: архитектура

## 1. Состав

```
art-active24-app/
├── api/        PHP 8.1+ — REST API на сервере сайта, читает ТУ ЖЕ БД, что и CMS
├── ios/        Swift 5.9 / SwiftUI, iOS 16+, XcodeGen (сборка в CI на macOS)
├── android/    Kotlin / Jetpack Compose, minSdk 26, Gradle KTS
├── contract/   openapi.yaml — единственный источник правды по API (оба клиента и сервер)
├── tools/      снятие dev-снапшота каталога (фид + страницы сайта)
└── docs/       архитектура, модель данных, дизайн-система, UX-спека
```

## 2. Почему между приложением и БД стоит API

Приложение не ходит в MySQL напрямую: логин/пароль БД оказались бы в каждом
установленном APK/IPA, а любой мог бы читать/портить данные. Схема:

```
iOS / Android ──HTTPS/JSON──▶ api/ (PHP, на сервере сайта) ──PDO──▶ MySQL сайта (CMS)
                                         └──────────────▶ новые таблицы app_* (ЛК, заказы)
```

API — тонкий слой: каждый эндпоинт = репозиторий, который собирает сущность со всеми
связями (товар → комплекты-26 → допы → характеристики → категории → похожие → площадки).
Логика цены (комплект × время × количество + допы) живёт на сервере и дублируется
в клиенте только для мгновенного предпросмотра; итог корзины всегда пересчитывает сервер.

### Источник данных каталога — за интерфейсом

`CatalogRepository` (интерфейс) имеет две реализации:

| Реализация | Когда | Откуда данные |
|---|---|---|
| `MysqlCatalogRepository` | прод | таблицы каталога CMS (товары, комплекты, разделы, параметры, площадки) |
| `SnapshotCatalogRepository` | разработка, пока нет доступа к БД | JSON-снапшот (dev-фикстура, `tools/snapshot`) |

Клиенты не знают, какая реализация работает: контракт один. Переключение — `CATALOG_SOURCE`
в конфиге. Снапшот — dev-фикстура, а не обходной путь в прод.

### Собственные таблицы приложения (на сайте их нет)

`app_users`, `app_auth_codes`, `app_sessions`, `app_addresses`, `app_favorites`,
`app_carts`, `app_cart_items`, `app_orders`, `app_order_items`, `app_order_status_log`,
`app_push_tokens`. Создаются миграциями `api/migrations/*.sql`; в dev — SQLite, в прод — MySQL
(SQL пишется в общем подмножестве).

## 3. Личный кабинет и заказы

- Вход по номеру телефона + код из SMS (провайдер за интерфейсом `SmsSender`; dev — код в логе).
  Access-токен (15 мин) + refresh-токен (60 дней, ротация), хранение: Keychain / EncryptedSharedPreferences.
- Гость может собирать корзину; при входе гостевая корзина сливается с серверной.
- Оформление повторяет сайт (корзина → дата/адрес/контакты → заявка). После отправки заказ
  создаётся со статусом **«В обработке»** и появляется в ЛК → «Мои заказы».
- Дальше статус двигает менеджер: `new → processing → confirmed → delivering → in_progress →
  completed` (+ `cancelled`). Каждое изменение пишется в `app_order_status_log`, пользователю
  уходит push. Менеджерский интерфейс — защищённый раздел `api/manager/` до интеграции в админку CMS.
- В заказе фиксируется снимок цен и названий на момент оформления (заказ не «плывёт»,
  если позже поменяли цены в каталоге).
- Карточка заказа в ЛК — три вкладки: **Обзор** (статус, машина на карте пока «В пути», отзыв после
  «Завершён», карточка претензии, неприметная ссылка «Что-то пошло не так?» с «Мероприятие идёт» до
  14 дней после завершения), **Состав** (разделы и итоги из «Программы КП» → от менеджера → из позиций
  корзины) и **Документы** (CRM, Вызов Чат, ссылки менеджера). Внешние системы — за интерфейсами
  (`OrderCompositionSource`, `VehicleLocationSource`, `OrderDocumentsSource`, `VyzovChatGateway`),
  боевые адаптеры выключены до получения доступа; сбой внешнего источника не ломает экран.
- Скидка постоянного клиента — уровень по сумме завершённых заказов (или персональная от менеджера),
  считается сервером после итогов строк и видна строкой «Скидка постоянного клиента −N%» в корзине,
  оформлении и заказе (см. DATA-MODEL.md).

## 4. Клиенты: общая архитектура (одинаковая на iOS и Android)

Слои: `Data` (DTO + API-клиент + кэш) → `Domain` (модели, расчёт цены, use-cases) → `Feature/*` (экраны).
Однонаправленный поток: экран ← ViewModel (состояние: loading / content / error / empty) ← репозиторий.

| | iOS | Android |
|---|---|---|
| UI | SwiftUI | Jetpack Compose (Material 3, своя тема) |
| Состояние | `@Observable` ViewModel, async/await | ViewModel + StateFlow, coroutines |
| Сеть | URLSession + Codable | Retrofit + kotlinx.serialization + OkHttp |
| Картинки | собственный кэш (URLCache + memory) | Coil |
| Хранение | Keychain, SwiftData/файлы для кэша | DataStore, EncryptedSharedPreferences, Room |
| DI | конструкторы + `AppEnvironment` | Hilt |
| Навигация | NavigationStack + TabView | Navigation Compose + bottom bar |
| Haptics | UIImpactFeedbackGenerator / sensoryFeedback | HapticFeedback / VibrationEffect |

## 5. Тактильность и «приятные» функции (обязательный слой, не «потом»)

См. `docs/UX.md`. Кратко: haptic на каждое значимое действие, свайпы и жесты везде, где
пользователь их ждёт, skeleton-загрузка вместо спиннеров, плавные переходы с общими элементами,
офлайн-кэш последних просмотренных, pull-to-refresh, undo вместо подтверждающих диалогов.
